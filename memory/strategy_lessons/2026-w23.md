## Lesson 1 — Four consecutive stale-data EOD sessions: escalation threshold needed

**Source:** June 1–4, 2026. The daily-bar provider failed to deliver a fresh close bar for four consecutive EOD windows, each time showing a bar 44–93 hours old. Per CLAUDE.md rule #5, each session produced `NO_TRADE (data_stale)` correctly. But the system had no mechanism to escalate after the 2nd or 3rd consecutive failure.

**Observation:** Each day, the routine (a) wrote a risk_event file, (b) flagged it prominently in the journal, and (c) emitted individual logs. None of these produced an operator-visible URGENT notification through Telegram or otherwise. The operator learned about the recurring issue by reading journals, not by receiving an alert.

**Pattern for future use:** When N consecutive EOD sessions all exit on `data_stale`, the operator needs an escalation signal — not just more of the same risk_event files. A lightweight streak counter (`logs/stale_data_streak.json` or similar) that fires an URGENT Telegram notification at N≥3 would have surfaced this issue on June 3 instead of June 6 (weekly review). The current design is silent escalation through accumulating files; the improvement is vocal escalation at a threshold.

**Proposed threshold (observations-only; not actioned in v1):** N=3 consecutive stale EODs → URGENT Telegram to operator. N=5 → recommend operator consider provider switch (formal action item in next monthly review).

**Implication for data provider:** When same-day pre_market reports fresh bars (e.g., 06-05 pre_market saw the 06-04 close), the EOD freshness is very likely to hold. The prior base-rate estimate (P(EOD-fresh)=0.35 given the stale streak) anchored too hard on the recent failure rate and underweighted the same-session fresh-bar signal. Rule to evaluate: when pre_market reports a fresh bar (age < 36h), P(EOD fresh) should be revised to ≥0.75, not held at the base-rate prior.

## Lesson 2 — Earnings calendar verification via LLM web search is not deterministic

**Source:** 2026-06-05 EOD. ORCL was rank-5 ENTRY, but earnings were confirmed for 2026-06-10 AMC (3 trading days out) via external web research (Oracle IR page / StockTitan / MarketBeat). This is inside the `holding_earnings_caution_window_days = 1` threshold (if open, pre_close would de-risk) and the spirit of the caution rule.

**Observation:** The confirmation was correct and the refusal was the right call. However, the process was: (1) LLM remembered the earnings date is "mid-June," (2) LLM fetched web sources to confirm. This process is non-deterministic — it depends on the LLM having training knowledge of the approximate timing, then confirming. If the LLM's training knowledge were wrong about the timing, the web fetch might not even be triggered.

**Pattern for future use:** A deterministic `data/earnings_calendar.csv` (or API-driven file) that is refreshed weekly would make this auditable, reproducible, and independent of LLM recall. The earnings date would be a first-class data point, not a research artifact. The cost is one additional data source to maintain; the benefit is reliable pre-earnings caution triggers without LLM dependency.

**Operational note for next week:** ORCL Q4 FY26 prints 2026-06-10 AMC. The pre_close routine on 2026-06-09 must flag any open ORCL position for de-risk (1 trading day before earnings = caution window trigger). If ORCL is opened on a 06-08 or 06-09 EOD, this must be a high-priority pre_close flag.

## Lesson 4 — META NaN close contaminates ranking silently

**Source:** 2026-06-04 pre_market and 06-05 pre_market. META showed a NaN daily close in the bar feed on June 4, causing it to appear as a spurious rank-1 (largest float in the 6-month-return sort when NaN is evaluated). The pre_market correctly identified the anomaly and excluded META. The issue self-resolved when the 06-05 close arrived cleanly.

**Observation:** A NaN close value propagating into `lib.signals.evaluate_all` corrupts the ranking: the NaN/null-return name sorts to either top or bottom of the universe depending on NaN handling in the sort. In this case, META sorted to top-of-rank (likely NaN → +∞ in the comparison). If the pre_market had not flagged it, META would have been included in the candidate slate with no valid thesis.

**Pattern for future use:** `lib.data.get_bars()` or `lib.signals.evaluate_all()` should include a pre-validation step: if `close` is NaN, zero, or negative for any watchlist symbol, that symbol is excluded from ranking and a `DATA_QUALITY_FLAG` is emitted into the signal output JSON. This prevents silent contamination and makes the exclusion auditable. The current behavior relies on a human-in-the-loop (the LLM reading the pre_market signal output) to catch NaN closes; that is not reliable under higher volume.
